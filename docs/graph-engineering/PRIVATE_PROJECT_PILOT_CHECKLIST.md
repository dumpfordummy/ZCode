# Private project pilot — user-operated authorization checklist

Status: **NOT RUN**. Z6 development uses isolated synthetic fixtures. No company repository, credentials, private integration, live model or publication is authorized by those fixture results. This checklist prepares a later explicitly named pilot; it neither starts one nor certifies suitability.

Record the authorized operator, date, repository identity, branch/commit or separately approved scratch copy, intended behavior, exact workflow/template version and human reviewers. Do not infer permission for a company repository from permission to develop this fork.

- [ ] **Target and baseline:** explicitly choose the workspace/identity and original versus scratch copy. Record HEAD, tracked/untracked baseline diff and preservation expectations. Keep the original worktree unchanged when a scratch target was selected.
- [ ] **Source authority:** name approved GameDoc/math/source references and their versions/digests. Identify affected Normal/Free/Bonus/Respin behaviors and explicit exclusions. Label missing rules as questions; require interpretation approval before implementation. An example template supplies no game rules.
- [ ] **Confidentiality:** define source, generated files, documents, logs, secrets and untracked content excluded from retained artifacts or later export. Review bounded source snapshots before approval. Do not copy a home directory, scan arbitrary credentials or export raw conversations by default.
- [ ] **Destinations:** inspect the actual resolved primary and auxiliary model configuration, including title generation; review Unknown destinations and their operational implications. Record approved network destinations. A local primary does not establish local-only traffic.
- [ ] **Native integrations:** review inherited project instructions, selected native skills, hooks, enabled plugins, MCP connections and native commands. Authorize any necessary external tool separately. Preview/import must not install, enable, connect or execute integrations.
- [ ] **Recipes/tooling:** discover actual project SDKs, solution/project paths, harness commands and package/feed access. Configure explicit existing native Build/Test recipes and required named criteria. Verify clean baseline commands in the selected authorized environment; missing tools/feed access remains a blocker.
- [ ] **Math acceptance:** where requested, record approved math/RTP target, sampling method, sample size and acceptance tolerance. Without these, mark math comparison N/A or blocked as appropriate. Aggregate RTP agreement never replaces targeted rule/edge-case tests and does not establish certification. Do not change authoritative source math merely to satisfy a target.
- [ ] **Permissions and ownership:** review the captured native permission mode and full-project access. Graph sequencing and recipe allowlisting are not an OS/filesystem/network sandbox. Confirm no unrelated Chat/editor writes will invalidate evidence. Do not silently elevate a mode or answer native questions automatically.
- [ ] **Execution bounds:** pin workflow version, graph revision, local bindings and configuration. Inspect repair limits where a supported bounded region is configured. Z6 slot tasks are sequential and have no default repair region; failed verification requires a new human decision.
- [ ] **Recovery rehearsal:** record owned run/node/session/input/operation IDs. Test cancellation against only those exact handles in an approved disposable run. Restart must not resubmit work. Continue only an eligible exact checkpoint; uncertain accepted work stays uncertain. Release requires the existing audited inactivity proof.
- [ ] **Human review:** name the source-interpretation reviewer and final diff/evidence reviewer. Review current test report provenance, targeted edge cases, structured findings and unresolved questions. Native permission decisions and graph approvals are separate. A reviewer saying PASS cannot override a failed test.
- [ ] **Evidence and conclusion:** record who performed each check, actual commands, IDs, outputs, screenshots and limitations. Keep controlled-fixture evidence separate from real-project evidence. Any unavailable check remains NOT RUN; a greeting or unrelated screenshot does not prove Read/Edit/test/restart behavior.
- [ ] **Publication:** commit, push, PR, merge, package, release, install-over or external sharing requires its own explicit scope. A graph approval is not authorization for publication.

The next milestone is not started by completing this checklist. Preserve the user’s native Chat, settings, history, source and existing packaging throughout the pilot.
