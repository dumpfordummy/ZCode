# Graph Engineering Z1

The window Host owns saved graph metadata and immutable attempts. The native Agent remains the only owner of sessions, input admission, tools, permissions and runtime state. See `docs/graph-engineering/Z1_SPEC.md` for product acceptance and event ordering.

Public UI contract is `contract.ts`; Node composition enters through `node.ts`. Domain validation is pure, app orchestration uses injected ports, and adapters perform asynchronous file/native service operations. Exactly Start -> one Agent Task -> End is supported. Stable request/command IDs are persisted before dispatch. Uncertain acceptance is never retried automatically. Only a matched live native terminal fact from the original runtime freezes a result; cold history cannot prove completion.

Native ordinary session creation allocates its own session ID. Graph persists run/attempt/input/command IDs before that call and persists the returned native session ID and runtime identity before observing or submitting. Supplied session IDs are reserved by the existing native API for imported history, which Z1 does not use. A lost creation reply stays Unknown without recreation or submission; its native session ID may be unavailable.

Initial attempt admission is transactional with metadata persistence: write a candidate record before adding it to the Host cache. If that first write fails, no native creation or submission occurs, no attempt is published or reserved in memory, and the caller may retry the same request after storage recovers. Uncertainty protection begins after the attempt has been persisted and native creation may have started.

Create with the same `deferred` persistence mode as ordinary native drafts. Native V4 admission promotes/persists the session before its input ledger write, and native indexing publishes the accepted task. The checkout's `immediate` creation can lack the parent session row and is not suitable for this V4 first-input path. The graph metadata already retains the returned session ID; observing its existing warm runtime does not itself submit or persist agent work.

One unresolved attempt per workspace identity/path is admitted. Unknown or interrupted work keeps the session input guard until explicit future reconciliation is implemented; this deliberately prevents accidental duplicate work in Z1. Session views and native interaction responses remain accessible. No graph operation changes provider settings or permission mode. Runs require the existing AskUserQuestion auto-resolution setting to be disabled.
Native dispatch and subscription carry an expected runtime identity. The Host binds those operations to the existing client for that identity and never starts a replacement process for them. A process change fails closed before dispatch; it cannot turn a stale graph operation into a new native input.

Rejected native input retains the native user-facing acknowledgement message together with its reason code, bounded to 2,000 characters; the adapter never serializes the acknowledgement object into diagnostics.

Unresolved graph sessions require explicit question responses. The Host supplies their IDs to the existing workspace interaction-preference synchronization; the native registry excludes those sessions from automatic question resolution even if the user later enables the global preference. Ordinary sessions continue following that preference. Graph admission still requires the existing preference to be disabled and never writes settings.

The existing `workspace/updateInteractionPreferences` request accepts optional `protectedSessionIds`: an authoritative replacement list of sessions whose questions require human responses. The native interaction registry applies that exclusion before registering future questions and synchronously cancels pending countdowns before acknowledging a preference update. A queued timer or expired-history microtask must recheck eligibility before resolving. Removing an exclusion never restarts an already snoozed question. Legacy requests that omit the field retain the current exclusion set. Protection follows native parent/child session ownership; it is runtime policy, not persisted application settings. Tests must show ordinary questions still time out while protected pending, new and restored questions do not auto-answer.

Graph metadata has one owning Host per workspace key across windows. The repository holds the existing PID/token file lock for the Host lifetime; another window may read the latest metadata but cannot write, reconcile or dispatch until ownership is released. Lock contention returns a bounded unavailable result, while filesystem failures remain errors. A disposed repository releases every acquired lock, including an acquisition completing during disposal. This lock protects graph metadata only; it does not lock project files or ordinary chat execution. Existing abandoned-lock recovery applies after a Host exits. Tests use independent repository instances and synthetic temporary directories to prove contention, release, re-acquisition and disposal races.
