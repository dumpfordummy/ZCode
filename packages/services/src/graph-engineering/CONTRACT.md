# Graph Engineering

Z7 adds the optional `parallel-contract.ts` facade under `docs/graph-engineering/Z7_SPEC.md`. The same GraphState/record/Host lease owns a bounded explicit Fork/Join plan and immutable parent runs; existing GraphEngineeringService child runs remain the only native attempt owners. Worker/integration/validation children use separate real app-owned local clones and persisted request IDs. The parent freezes clean base/configuration/scopes, limits concurrency/admissions/deadline, captures complete proposals, requires explicit conflict/integration decisions, verifies the actual integrated diff and runs fresh native Build/Test plus the existing final Human Approval. Cold reads never dispatch. Cleanup is explicit and requires owned-path validation, authoritative inactivity and absent runtime. Optional record fields preserve older sequential data without reinterpretation. This is not a general nested workflow API or an OS sandbox. See the spec for event order and unsupported behavior.

Z6 adds `workflow-contract.ts`: a profile-local immutable workflow library, dry portable transfer, explicit local instantiation through the existing Graph save owner, and native execution preparation. See `docs/graph-engineering/Z6_SPEC.md` and `Z6_NATIVE_SPEC.md`. A version-5 graph may carry a frozen template pin; its run requires a matching reviewed preflight and retains reference/configuration provenance. Semantic drift stops future admissions. This optional extension does not migrate or reinterpret existing records. The library has its own revision-checked atomic storage; it owns neither sessions nor execution. Portable operations never call native discovery or perform installation/network/script actions.

Z3 adds the explicit version-3 Human Approval control contract in `docs/graph-engineering/Z3_SPEC.md` and bounded read-only native source evidence in `docs/graph-engineering/Z3_SOURCE_SPEC.md`. The public `contract.ts` re-exports approval DTOs from `approval-types.ts`; no new engine or service channel exists. Native attempts remain separate from approval attempts. Pending requests, exact decision idempotency and a single successor intent persist under the same Host owner. `decideApproval` and `continueApproval` are explicit commands; viewing history never advances work. The current saved graph and selected evidence are checked before decision, cold continuation and immediate successor creation/send. Stale/incomplete evidence cannot authorize; cold pending/approved-undispatched gates require explicit continuation; uncertain native phases retain Z2 recovery. Version-2/Z1 history retains its original semantics.

Z2 extends this contract under `docs/graph-engineering/Z2_SPEC.md`. Version-2 definitions/runs are explicit unions with the unchanged unversioned Z1 formats. Save accepts shaped incomplete Z2 drafts; `validateDefinition` supplies authoritative readiness/path diagnostics. Run freezes every node's native settings and Start text, resolves explicit one-pass bindings, and serializes fresh native sessions. All unresolved run sessions remain guarded. Node outputs and terminal proof persist before any successor dispatch. Inspect/release are explicit, read-only reconciliation followed by audited inactive-only release; neither replays work. The sections below document retained Z1 integration invariants; Z2 now supplies the previously deferred reconciliation surface.

The window Host owns saved graph metadata and immutable attempts. The native Agent remains the only owner of sessions, input admission, tools, permissions and runtime state. See `docs/graph-engineering/Z1_SPEC.md` for product acceptance and event ordering.

Public UI contract is `contract.ts`; Node composition enters through `node.ts`. Domain validation is pure, app orchestration uses injected ports, and adapters perform asynchronous file/native service operations. The unversioned Z1 form remains Start -> one Agent Task -> End; version 2 adds sequential tasks and version 3 adds Human Approval controls. Stable request/command IDs are persisted before dispatch. Uncertain acceptance is never retried automatically. Only a matched live native terminal fact from the original runtime freezes a result; cold history cannot prove completion.

Native ordinary session creation allocates its own session ID. Graph persists run/attempt/input/command IDs before that call and persists the returned native session ID and runtime identity before observing or submitting. Supplied session IDs are reserved by the existing native API for imported history, which Z1 does not use. A lost creation reply stays Unknown without recreation or submission; its native session ID may be unavailable.

Initial attempt admission is transactional with metadata persistence: write a candidate record before adding it to the Host cache. If that first write fails, no native creation or submission occurs, no attempt is published or reserved in memory, and the caller may retry the same request after storage recovers. Uncertainty protection begins after the attempt has been persisted and native creation may have started.

Create with the same `deferred` persistence mode as ordinary native drafts. Native V4 admission promotes/persists the session before its input ledger write, and native indexing publishes the accepted task. The checkout's `immediate` creation can lack the parent session row and is not suitable for this V4 first-input path. The graph metadata already retains the returned session ID; observing its existing warm runtime does not itself submit or persist agent work.

One unresolved attempt per workspace identity/path is admitted. Unknown or interrupted work keeps the session input guard until a matched terminal result or explicit audited confirmed-inactive release; release never resumes unknown work. Session views and native interaction responses remain accessible. No graph operation changes provider settings or permission mode. Runs require the existing AskUserQuestion auto-resolution setting to be disabled.
Native dispatch and subscription carry an expected runtime identity. The Host binds those operations to the existing client for that identity and never starts a replacement process for them. A process change fails closed before dispatch; it cannot turn a stale graph operation into a new native input.

Rejected native input retains the native user-facing acknowledgement message together with its reason code, bounded to 2,000 characters; the adapter never serializes the acknowledgement object into diagnostics.

Unresolved graph sessions require explicit question responses. The Host supplies their IDs to the existing workspace interaction-preference synchronization; the native registry excludes those sessions from automatic question resolution even if the user later enables the global preference. Ordinary sessions continue following that preference. Graph admission still requires the existing preference to be disabled and never writes settings.

The existing `workspace/updateInteractionPreferences` request accepts optional `protectedSessionIds`: an authoritative replacement list of sessions whose questions require human responses. The native interaction registry applies that exclusion before registering future questions and synchronously cancels pending countdowns before acknowledging a preference update. A queued timer or expired-history microtask must recheck eligibility before resolving. Removing an exclusion never restarts an already snoozed question. Legacy requests that omit the field retain the current exclusion set. Protection follows native parent/child session ownership; it is runtime policy, not persisted application settings. Tests must show ordinary questions still time out while protected pending, new and restored questions do not auto-answer.

Graph metadata has one owning Host per workspace key across windows. The repository holds the existing PID/token file lock for the Host lifetime; another window may read the latest metadata but cannot write, reconcile or dispatch until ownership is released. Lock contention returns a bounded unavailable result, while filesystem failures remain errors. A disposed repository releases every acquired lock, including an acquisition completing during disposal. This lock protects graph metadata only; it does not lock project files or ordinary chat execution. Existing abandoned-lock recovery applies after a Host exits. Tests use independent repository instances and synthetic temporary directories to prove contention, release, re-acquisition and disposal races.

# Z4 extension

The explicit Z4 assignment extends this same owner with version-4 immutable run artifacts, optional strict structured output and sequential deterministic Tool nodes. See `docs/graph-engineering/Z4_SPEC.md` and its native/artifact contracts. Native CLI services retain process execution and permissions; Graph persists intent/evidence and admits successors only after exact verified results. Z1–Z3 meanings and history remain valid, reads never execute, and uncertain commands are never replayed. Artifact content is app-owned, bounded, ownership/digest checked and excluded from exports by default. No parallel scheduler or second command engine is introduced.

# Z5 extension

`docs/graph-engineering/Z5_SPEC.md` defines explicit version-5 typed Conditions, exclusive branches and one bounded repair region. `routing-types.ts` carries declarative predicates, finite limits, immutable iterations, exact attempt maps and persisted route checkpoints. The same serialized Host owns cursor advancement, admission reservations and deadline cancellation. Each repair gets fresh native sessions; historical attempts and artifacts remain immutable. Trusted native Test verification observations distinguish failed assertions from invalid provenance without relaxing Z4 artifact acceptance. Decisions persist before successors. Cold checkpoints require explicit `run({action: "continue", ...})`; uncertain creation/submission is never replayed. Every End route requires the final Human Approval. Renderer iteration selection is only a projection and never changes execution ownership.
